Icon button — standardized GAP — real color values, sizing/no-border is a direct design decision for WCAG 2.2 AA compliance

Every icon-only clickable button in production today (the record-detail kebab menu, and any others styled the same way) uses the class name kebab-btn — but there is no .kebab-btn rule anywhere in mdb-customizations.css or mdb_min.css. The class is a JS/dropdown hook only; every actual instance repeats the identical look via a copy-pasted inline style="" attribute, with no explicit size at all — width and height fall out incidentally from padding plus whatever font-size happens to be inherited. That's two separate problems: no enforced consistency, and no guaranteed target size.

WhatOne .icon-btn class for any icon-only clickable control — row-menu triggers, delete, edit, download, anywhere an icon alone is the whole button.
Where24×24px, one size, everywhere — including dense contexts like table rows, where the earlier 32px draft read too heavy.
WhenUse .icon-btn for any new icon-only action. Don't reach for a bare <i> wrapped in a plain <button> or <a> with ad hoc inline sizing — that's exactly the drift this consolidates.
WhyWCAG 2.2 SC 2.5.8, Target Size (Minimum), Level AA: pointer targets must be at least 24×24 CSS pixels, with narrow exceptions (inline text, essential presentation, an equivalent control elsewhere, adequate spacing) that don't apply to a standalone icon button. 24×24 is the exact floor — not a comfort margin above it, so there's no smaller "sm" variant to accidentally reach for. No border: 2.5.8 governs the tappable area, not visual styling — hover and focus-visible states carry the affordance instead.
HowEvery icon-only button needs a real aria-label. There's no visible text for a screen reader to announce, so without one the control has no accessible name at all — this is WCAG 1.1.1 (Non-text Content) and 4.1.2 (Name, Role, Value), both Level A. title alone is not sufficient; it's inconsistently exposed to assistive tech.
<button type="button" class="icon-btn" aria-label="More actions"> <i class="fa-regular fa-ellipsis-vertical"></i> </button> .icon-btn { display: inline-flex; align-items: center; justify-content: center; width: 24px; height: 24px; background: none; border: none; border-radius: 4px; padding: 0; cursor: pointer; color: var(--colors-brand-primary-dark-blue); font-size: 14px; line-height: 1; } .icon-btn:hover { background: var(--colors-state-layers-light-hover); } .icon-btn:focus-visible { outline: solid 2px var(--colors-brand-primary-dark-blue); outline-offset: 2px; } .icon-btn:disabled { opacity: 0.5; cursor: not-allowed; }

Icon color is the same real value found on production's kebab button. Sizing and border are direct design decisions, corrected twice now: the first pass had no explicit width/height at all (incidental sizing, a real WCAG risk); the second pass fixed that with a 32×32 default plus a 24×24 "dense-context" variant, but 32px read too heavy in practice — table rows in particular — so the default is now 24×24 everywhere, exactly the WCAG floor, with no smaller variant needed since there's nothing left to shrink from. The border from production's real kebab-btn instance was also removed on direct instruction: WCAG 2.5.8 requires the tappable area to be 24×24, not a visible border — that was never a compliance requirement, just what one real instance happened to look like. Hover and focus-visible carry the visual affordance at rest and on keyboard focus instead. aria-label is not optional; every example above includes one. Needs engineering review before it round-trips into mdb-customizations.css, since it would mean replacing inline styles (and removing the border) at every existing call site.

Focus treatment GAP — resolution proposed, not yet in production

.navbar-brand:focus-visible, .navbar-nav > li > a:focus-visible, .navbar-nav a.nav-link:focus-visible { outline: solid 2px currentColor; outline-offset: 2px; }

No .navbar-nav or .navbar-brand focus override exists anywhere in production today; keyboard focus currently falls back to the browser's own default focus indicator (color varies by browser). .navbar-brand is included here alongside .navbar-nav since it's structurally a sibling, not a child, of .navbar-nav — a rule scoped only to .navbar-nav would miss the logo entirely. This proposal uses currentColor rather than a fixed navy outline, deliberately: per the "Why" row above, header/footer background is an org-brandable slot, and individual foundations inject their own background and paired text color together. A fixed navy outline could fail WCAG 1.4.11 (3:1 non-text contrast) the moment an org picks a dark background. Inheriting currentColor means the outline automatically gets whatever text color the org already had to choose for legibility, no separate light/dark branching, and it can't drift out of sync with the org's own choice later. This is part of a system-wide focus-state consistency pass (see Buttons, Text Inputs, Checkbox/Radio/Switch, and Sidenav) — buttons already ship the fixed-navy version of this same outline in production; Navbar is the one component where that fixed color isn't safe. Needs engineering review before it round-trips into mdb-customizations.css.

Icon usage in buttons RATIFIED

Checked every real .btn in the production sample: 19 total, 1 with an icon — and that one (.kebab-btn) is icon-only, not a text+icon combo. Every button that has a label is text-only. That's the rule now, not an aspiration: default to text-only, with one deliberate, curated exception below. .kebab-btn stays its own separate pattern — icon-only, never paired with a label.

<!-- The one sanctioned exception: primary "create new" actions --> <button class="btn btn-primary"><i class="fa-light fa-plus me-2"></i>New</button> <!-- Icon-only stays its own separate pattern, never combined with a label --> <button type="button" class="kebab-btn" aria-label="More actions"><i class="fa-regular fa-ellipsis-vertical"></i></button> /* Full rule (explicit 24x24 sizing, no border, focus-visible, WCAG 2.2 AA) lives in the Icons section under "Icon button — standardized" — not repeated here to avoid two copies drifting apart. */

Ratified decision, not a draft. Exception list: primary "create new" actions only (+ New, + Add) — the + is a near-universal affordance and these buttons recur often enough across list/table views to benefit from a scan-target. Everything else is text-only: Edit, Save, Cancel, Delete, Confirm, Submit, Download — no icon, no exceptions. Modals follow this too — confirmed (Section on Modals) footer buttons are already text-only in the real example checked.

Frequency rule, decision not evidence: an icon+text button should appear at most once per page — it's reserved for a single primary action, not a general-purpose style. Only use the + when the action is genuinely additive (creating something new); don't reach for it as decoration on an already-text-only button. Icon-only buttons (.icon-btn/.kebab-btn) can be used far more liberally — they're compact enough not to compete for attention the way an icon+text combo does, so repeating them across a page (row menus, table actions) doesn't create the same visual noise.
