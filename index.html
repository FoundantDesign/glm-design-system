Colors PROPOSED UX-130 UX-132 UX-140

Rule:DESIGN-SYSTEM.md › Tokens

Foundant color tokens, defined in foundant-tokens.css. Components use them through --mdb-* remaps, never as raw values.

WhatThe token palette: brand, the primary tint ramp, neutrals, semantic colors, state layers and borders.
Where--colors-* custom properties in foundant-tokens.css, consumed by mdb-customizations.css.
WhenNavy primary for text, headings and primary actions. Neutrals for surfaces, dividers and muted text. Semantic colors only for state. Text on any -50 tint is navy.
WhyOne palette keeps every surface consistent, and changing a token updates everything that uses it.
Howcolor: var(--colors-brand-primary-dark-blue) in CSS, or a utility class that already maps to a token (.text-muted, .text-danger). No hex values outside token definitions.

Typography SHIPPED

Roboto throughout, with a compressed heading scale for a data-dense app.

WhatThe heading scale, h1 to h6, and body text, all in Roboto through --body-font.
WhereBare h1 to h6 elements, sized by --h1-size to --h6-size. The .h1 to .h6 utility classes keep MDB's sizes.

Rule:DESIGN-SYSTEM.md › Icons

Font Awesome Pro 7, self-hosted as a curated subset. fa-light by default, fa-regular for filled-state controls.

WhatFont Awesome Pro icons, converted to inline SVG at runtime.
Where<i class="fa-light fa-…"> in markup. In GLM.Web views, the Icons.Classic.* helpers.
WhenLight everywhere. Regular for filled-state controls such as toggles and the kebab menu. Duotone only as an accent on summary pages.

Spacing & Radius PROPOSED UX-141

Rule:DESIGN-SYSTEM.md › Radius

Bootstrap spacing utilities and the Foundant radius scale.

WhatSpacing comes from Bootstrap's m-*, p-* and gap-* utilities. Corners come from the --radius-* tokens.
WhereSpacing as utility classes in markup. Radius as tokens in CSS: none 0, xs 2px, sm 4px, card 6px, md 8px, round 50px.
WhenButtons are always round. Inputs and badges use sm. The hero card uses card. Larger surfaces use md.
WhyA fixed scale keeps corners and gaps consistent without custom margins.
Howclass="mt-2 mb-3" for spacing, border-radius: var(--radius-sm) in CSS. Stat tiles still use an off-scale 10px radius (UX-141).

Radius scale

Spacing utilities

Bootstrap scale: p-1 4px · p-2 8px · p-3 16px · p-4 24px · p-5 48px. Same values for margins (m-*) and directional variants (mt-, px-, etc.).

Breadcrumb PROPOSED UX-152 UX-153

Rule:DESIGN-SYSTEM.md › Stock MDB components

Ancestor trail for nested records. Stock MDB in production.

WhatMDB .breadcrumb on an <ol>, one .breadcrumb-item per level, with .active plus aria-current="page" on the final item. Wrap in <nav aria-label="breadcrumb">.
WhereStock MDB. Production has no breadcrumb rules, so the current item looks the same as its links (UX-152).
WhenOnly where a record genuinely sits inside a hierarchy the user can navigate up through (organization to request to award). Not as a substitute for a page title, and not on a top-level list page where the trail would be one item long.
WhyThe trail shows where a record sits. Marking the current item, visually and with aria-current, tells people where they are.
HowDefault padding is zero on both axes with a 1rem bottom margin, so the component carries no background or box of its own and sits directly in page flow.

Buttons PROPOSED UX-133 UX-130

WhatMDB buttons, the main action control across GLM.
Where.btn plus a variant. Page actions, card headers and modal footers.
When.btn-primary for the main action. .btn-outline-dark.fw-bold is the record page default; .btn-dark.fw-bold.shadow-none the card primary action. .btn-outline-secondary for secondary (.btn-secondary is banned). Danger for destructive actions.
WhyEvery button is a pill, and variants remap MDB's button variables onto tokens, so no button needs its own class.
HowDefault .btn is 32px. Add .btn-sm (24px) only in table rows and in-grid chrome. Labels are text only, except one + New or + Add per page.

Shadow is for page structure only.

WhatTwo real production shadow values. A page-chrome shadow on header, footer and .page-container, and a directional inset on .left-view-selected / .right-view-selected. Everywhere else, shadow is switched off.
WherePage chrome only: header, footer and .page-container, plus the directional inset on .left-view-selected and .right-view-selected. .card has no shadow.
WhenUse the chrome shadow only for structural page furniture that separates a surface from the page behind it. Do not add shadow to a card, button or badge to make it stand out; that is what spacing and borders are for in this system.
WhyGLM reads as a flat, bordered interface rather than a layered Material one. Removing MDB's default shadows is the larger half of the decision, and it is deliberate rather than incidental.
HowThe inset directional shadows are a split-view affordance: the selected side casts a shadow toward the divider, so the two panes read as overlapping rather than abutting. Mirror the direction to match which side is selected.
